### 1.2 團隊實際運作

1. 版本號 `0.<中>.<小>`：中版號是主要迭代，每版開版本分支 `0.xx.0`；小版號只用於 hotfix；版本完成時提交 `RLS_0.xx.x`。
2. 議題分支以 squash 合併進版本分支，合併後保留原分支，分支內的 commit 可追溯。
3. 合併者為資深工程師或主管，reviewer 不一定是合併者；review 標準未成文，現行順序大致為功能正確、符合規範、測試通過，最後才看效率與架構。
4. MR 描述（merge log）含目標版本、`by <名字>` 與條列，條列前綴規範是 `新增` / `修改` / `刪除`，但人工撰寫的風格不一致。
5. 分支後綴未成文：`_2nd`、`(2nd)`、`_V2`、`_merge`、`_Rebase` 並存。
6. 沒有自動測試與 CI，驗證靠人工與個別議題的腳本。
7. 研發文件剛開始試行，已有共識放在 `Doc/<議題編號>/`，結構與命名尚不一致。
8. 開發工具：全員使用 GitHub Copilot，部分成員使用 Claude Code；Visual Studio 統一使用 2026（18 版以上）。

### 1.3 問題

1. 團隊流程只存在個人設定，團隊與其他成員的 AI 讀不到。
2. 流程規則與技術規範沒有依「何時需要」區分，全部常駐會占用 AI 的 context。
3. 流程成本沒有隨議題大小調整，小議題缺少精簡的最低產出。
4. Review 標準、完成定義、分支後綴、文件結構都沒有成文，每個人做法不同。
5. 文件的項目編號用單一字母（`R`、`S`、`T`），難以辨識。
6. 現行 Coding Style 要求「同一方法維持既有命名」，與「新程式碼採新規範」的方向衝突；也沒有規定 Production Code 不引用文件。

## 2. 目標

建立人與 AI 共用的開發流程規範：團隊規範以 repo 為唯一來源，Copilot 與 Claude Code 讀同一份；依讀者與使用時機分層，常駐內容精簡；流程成本隨議題級別調整；review 與完成標準可檢查。

## 4. 需求

### REQ-1 規範分層

1. 規範分為四層：入口、團隊通用、MyCAM 專案、個人。
2. 團隊通用的流程不含 MyCAM 專屬內容，可直接搬到團隊其他 repo；MyCAM 專屬內容（建置、多語系、Designer、專案固定檢查項目）只寫在專案指引及其子層。
3. 入口文件只說明規範如何分類與讀取，不定義規範本身。

### REQ-2 工具共用

1. Copilot（VS 2026 18 版以上）與 Claude Code 讀同一份規範，內容不重複維護。
2. 只用其中一種工具的成員，也能完整遵循流程。

### REQ-3 載入時機

1. 常駐內容只放每次互動都適用的規則，總量精簡。
2. 流程本文不常駐；常駐的索引明列「時機 → 必讀文件」。
3. 最常主動觸發的動作（開議題、review、產出 release note）提供可直接呼叫的入口。

### REQ-4 議題分級與完成定義

1. 定義 S、M、L 的判斷依據、處理階段與各級確認點。
2. 每級訂定最低必要產出與完成定義（DoD），S 級精簡。
3. 施工中發現範圍超出級別時，有重新分級的規則；後段（含 review）發現前段內容要修改時，有回溯的規則。
4. 確認點的待討論問題有固定格式，不需回溯前文就能判斷：寫明問題（背景與要決定什麼）、建議（做法與理由）、另一可行選項（做法與取捨）；在文件與對話中都適用。

### REQ-5 議題文件

1. 存放於 `Doc/<議題編號>/`，同一議題的後續 MR 沿用同一資料夾；`SESSION.md` 不提交，只放交接內容。
2. 各級的檔案組合與每塊內容的歸屬明確（哪些獨立成檔、哪些併入 `README.md`）。
3. 項目編號使用可辨識的前綴：`REQ`、`SPEC`、`TEST`、`STEP`、`TODO`、`DEC`、`REV`。
4. 文件只保留最終結果，議題結束後長期有效的結論提升到指引規範。
5. 所有規範指引與議題文件都要精簡，「精簡」有明確可檢查的定義；自動載入的內容另設硬上限，review 時檢查。

### REQ-6 Review

1. 依序檢查：自動門檻、需求與範圍、功能正確性、規範符合、設計品質、文件。
2. 明定每段由人或 AI 負責；AI 負責可量化的檢查，人負責實機操作、需求判斷與設計取捨。
3. 不論使用哪種工具，review 報告格式一致，每項發現都有處置。

### REQ-7 Git 流程

1. 成文化現行的版本號、版本分支與 squash 合併、分支保留。
2. 分支命名統一，含後續 MR、送 MR 前自測回合、並存實作、rebase 暫存分支的規則。
3. Commit 規則：每個實作步驟一個 commit，文件、測試、程式盡量分開。
4. Release note 只含 `新增` / `修改` / `刪除` 條列，由 AI 產出；merge log 由 AI 依格式提供，目標版本留空。

### REQ-8 Coding Style 修訂

1. 童子軍法則：新增與修改的程式碼採新規範；同一方法新舊混用到難以閱讀時，可將該方法改為新規範，格式調整獨立 commit；不修改未動到的方法。
2. Production Code 註解不引用文件、測試或規範條目；難解釋的特例最多留議題編號。

### REQ-9 個人設定收斂

1. `~/.claude/issue-workflow.md` 的內容移入 repo 後刪除，個人設定只保留個人偏好。
2. `github` remote 的用法寫在 `CLAUDE.local.md`。

### REQ-10 後續議題

1. 範圍外項目寫入 `FollowUp.md`，每項寫明目標、完成條件與延後原因，讓接手的 session 不需要回溯本議題的討論。
2. 至少包含：使用手冊維護機制、自動化品質門檻（本機檢查、CI、測試專案分階段）、MR 建立自動化、既有分支依新規範調整。
