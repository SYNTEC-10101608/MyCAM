## 14.4 待討論問題

| ID | 優先度 | 問題 | 分類 |
| --- | --- | --- | --- |
| R4-01 | 優先（測試可靠性） | N2 用等待迴圈回傳時的清單代替通知時間，既可能誤報，也未涵蓋完整 interval 下限 | 測試時間 oracle／文件對應 |

本項是一個時間判定問題，影響 `CheckDebounceMerge` 一個方法；下列誤報與時間盲區是兩種證據，不計為兩個產品 bug。

### A. UI 訊息泵延遲時，合法通知也被當成提早通知

`Tools\UICheck\ControlRunner.cs:117–133`：第二次改值後以 `PumpUntil(..., 400)` 等待，再斷言通知清單必須為空。

但 `262–268` 的 while 只在進入本次迴圈前檢查 timeout，接著呼叫 `Application.DoEvents()`。這次訊息處理若跨過期限，合法的晚通知可能已加入清單，回到斷言時仍一律被判為「間隔內通知」。單純改大 timeout／延長最後等待，不會修正分類方式。

**未修改產品與測試來源的重現**：

1. 將現行 ControlRunner 編譯為臨時組件，以反射直接呼叫原本的 `CheckDebounceMerge`。
2. 以另一個 WinForms Timer 在該方法的訊息泵中製造 250ms 的 UI 執行緒延遲。
3. 現行方法報出：`N2 no notification within the interval after the last change: DebouncedValueChanged expected [], got [21]`；問題數為 1。
4. 另以相同原始 `PumpUntil` 和現行數值框量測公開通知時間，確認不是產品先通知：

| 相對於最後一次改值的時間 | 觀察 |
| --- | --- |
| 約 364ms | 控制的 UI 執行緒延遲開始 |
| 約 629ms | 延遲結束 |
| 約 631ms | DebouncedValueChanged 通知，值 21；**已超過 500ms，不是提早通知** |
| 約 646ms | 原本 400ms 的 PumpUntil 才返回，清單已有一筆 |

這是有條件、已實測的誤報，不宣稱普通機器每次都會失敗。GC、排程或訊息處理延遲都可能讓觀察跨過期限；本輪用控制的停頓建立該條件。測試使用真實 WinForms Timer 與訊息泵是合理的，**問題不是看到 Thread.Sleep 就判定反模式，而是 oracle 沒有記錄通知發生時刻**。

### B. 400～500ms 的提早通知仍未被保護

`.github\instructions\ui-style.instructions.md:289–290` 與 5.1 的結果表要求／描述「不早於最後一次變化後的間隔」。當間隔是 500ms，只有前 400ms 無通知，不能證明剩下的 100ms。

具體候選：將 `DebouncedNumericUpDown.cs:33` 的 timer interval 指定值改為 `value - 50`。對現有 N2 的 500ms 設定，實際等待會變成約 450ms；在正常排程下，400ms 的空清單斷言仍可通過，後續清單仍是 [21]，但已違反 500ms 下限。其餘使用預設 interval 的案例不經此設定路徑。

| 公開序列 | 原行為 | 候選行為 | 分類 |
| --- | --- | --- | --- |
| 設 interval 500ms，改 20，約 200ms 後改 21 | 從最後一次變化起等待完整 interval，才通知一次 21 | 可能約 450ms 就通知一次 21；現有清單斷言不區分 | **Candidate survivor (unverified)**；沒有修改或執行此候選 |

已承認 4.17 的 400ms 窗口能抓原 Stop 移除案例；本項不是否定該驗證成果，而是指出它不能同時支撐回覆「兼顧穩定、沒有放寬不可提早」與文件的完整 interval 保證。

### 建議修正方向

保留最後值／次數斷言，新增通知時刻記錄，而不是對返回時的清單要求一律為空：

1. 在最後一次 `Value` 指定前記錄單調時間，避免量測起點落在 timer 已啟動之後；在公開 DebouncedValueChanged 回呼中記錄通知時刻與值。
2. 斷言最後只有一次值 21，且首次通知相對於最後變化的時間不早於完整設定 interval。允許 OS 造成較晚通知，不以觀察迴圈回來較晚為失敗理由。
3. 若保留早期觀察窗口，應以已記錄的事件時間判斷有沒有早於門檻的事件，不以觀察結束後整份清單是否為空判斷。
4. 保留原 Stop 移除的反向案例，再補較小幅提早的案例與 UI 排程延遲的正向案例。計時器解析度的處理須有明確依據，不能以 100ms 未觀察區代替完整 500ms 契約。

不需要為此新增產品專用測試旗標、時間 API 或更改正確的 debounce 行為；最小修正面是 N2 的時間記錄、判斷與直接相關文件。
